# Web app: decisions and deviations from earlier phases

| ID | Decision | Replaces / differs from | Why |
|---|---|---|---|
| W-01 | PostgreSQL 16 | Phase 1 D-03 (MongoDB) | Requested for the web app. Relational integrity (composite FKs, CHECKs, real transactions) replaces Mongo's "unique index + discipline". |
| W-02 | `tenant_id` on every table plus RLS | Phase 5 finding D-3 (no tenant isolation) | Required for multi-tenant hosting. Restores the Phase 1 design. |
| W-03 | No Redis/BullMQ: Postgres outbox with `SKIP LOCKED`, `LISTEN/NOTIFY` for real time | Phase 4/5 BullMQ | The outbox row is written in the same transaction as the business change, so "committed but never queued" cannot happen, and there is one less service to run. |
| W-04 | CLOSED_WON is final; CLOSED_LOST reopens to FOLLOW_UP with a reason | Phase 3/5 rules (Closed-Won -> Negotiation) | Re-winning a lead would bill twice. Enforced by trigger as well as code. |
| W-05 | Integer paise + gapless sequential invoice numbers | Phase 5 floats, `INV-<random>` | Phase 5 findings D-2 and section C. |
| W-06 | One account per e-mail address platform-wide | n/a | Login does not ask for a tenant. A person in two businesses needs two e-mail addresses. |
| W-07 | Mongo-era code kept under `legacy/mongo/` | n/a | Reference only (e.g. the Phase 4 e-mail "uncertain" logic being ported); not built or tested. |
| W-08 | Scraper runs in-process as a Postgres-queue worker; jobs are claimed by a `SECURITY DEFINER` function (`scrape_claim_next`) | Phase 2 one-shot CLI with Crawlee | The queue lives in the same database as the leads, so progress, cancel and tenant isolation need no extra service. Crawlee/Playwright were dropped: the generic adapter only needs static HTML, and a plain pinned-socket fetcher is much easier to make SSRF-safe. |
| W-09 | SSRF defence in depth: per-workspace domain allowlist, no IP literals/internal names/odd ports, resolve once + all answers public + socket pinned to that answer, every redirect hop re-vetted | Phase 2 `isSafeUrl` (checked once, then fetched by a library that resolves again) | The old check was open to DNS rebinding and redirects to internal hosts. |
| W-10 | robots.txt: longest-match with Allow winning ties, `Crawl-delay` honoured up to 10 s, 4xx = allowed, 5xx/timeout = do not crawl | n/a | RFC 9309 behaviour, erring on the side of not crawling. |
| W-11 | One scraped lead per business domain (`domain:<host>` dedupe key); a 2nd page of the same site counts as a duplicate | Phase 2 `website|email` key (one lead per address) | Matches the Phase 1 identity rules and the unique index. |
| W-12 | Members change only leads they own or that nobody owns; admins/owners change any. Reads are workspace-wide | Phase 3 "only the owner may transition" | Multi-user workspaces need an admin override, and unowned scraped leads must be workable. |
| W-13 | CSV import refuses cells starting with `= + - @ TAB CR` (phone cells are validated by pattern instead) | n/a | Stops formula injection at the door. Exports (stage 6) will additionally neutralise cells. |
| W-14 | Closing a lead as won is ONE transaction: client, lead status, history, invoice (next gapless number), items, queued e-mail | Phase 4/5 two-step "convert then reconcile" with a reconciler job | A failure anywhere rolls back everything, so a reconciler is not needed and a number is never burned. Proven by a test that forces the e-mail insert to fail. |
| W-15 | Issued invoices are immutable in the database (guard trigger, items append-only, PAID/VOID final) | Phase 5 (application-level only) | The app role itself cannot alter an issued invoice, whatever a future bug does. |
| W-16 | E-mail delivery is at-most-once: claim = durable SENDING before contacting the provider; unknown outcome or dead worker => UNCERTAIN, never auto-resent; humans resolve it | Phase 4 EMAIL_UNCERTAIN logic, ported to a Postgres outbox | Double-sending an invoice is worse than a delayed one. Definite rejection => FAILED; ordinary errors retry with back-off up to max_attempts. |
| W-17 | Invoice PDFs: file per invoice on local disk, sha256 in the DB, rebuilt from the immutable snapshot if missing/tampered | Phase 4 PDFs named by invoice number in one folder | Names come only from uuids (no traversal); integrity is checked on every read. Standard PDF fonts cover Latin-1 only: other scripts print as "?". |
| W-18 | Money: integer paise, BigInt arithmetic, half-up rounding per line, tax per line in basis points | Phase 5 floats | Lines always add up to the total. |

## Stage 5b: frontend

- **W-19 Access token in memory only.** The JWT lives in a module variable, never localStorage/sessionStorage, so XSS cannot read a long-lived credential. A page reload restores the session through the httpOnly refresh cookie. Concurrent 401s share one refresh call because refresh tokens are single-use.
- **W-20 One origin in dev.** Vite proxies `/api` to :3000 so the SameSite=Strict refresh cookie and the CSRF cookie behave exactly as in production behind a reverse proxy. No CORS is needed in dev.
- **W-21 SSE via fetch.** EventSource cannot send `Authorization`, so the stream is read with fetch and a small parser. Events carry ids only; each one invalidates TanStack Query caches (coalesced over 250 ms), and every (re)connect invalidates everything because events may be missed while offline.
- **W-22 No drag-and-drop.** The board moves leads with a "Move to…" control restricted to `allowedNext` from the server; it works with touch, keyboard and screen readers. Moves are optimistic and roll back from a cache snapshot on error (including version conflicts).
- **W-23 UI hides, server enforces.** Menus and actions follow `permissions` from `GET /api/me`; every route is still authorised server-side.
- **W-24 Offline.** The service worker precaches the app shell only. `/api/*` is never cached (live, private data); offline the shell loads and views show an error state with retry.

## Stage 6: hardening

- **W-25 Headers.** Helmet on every response. API paths get `default-src 'none'; frame-ancestors 'none'`; the optional bundled SPA (`WEB_DIST_DIR`) gets a strict CSP (own-origin scripts and styles only, no inline script, no eval, no objects, no framing). HSTS (2 years, includeSubDomains, preload) only when `NODE_ENV=production`, so local http is never pinned. The theme bootstrap script is an external file so the CSP can forbid inline scripts.
- **W-26 CORS.** A hand-written allowlist (not a permissive library). Allowed origins get exact-match `Access-Control-Allow-Origin` plus credentials; everything else gets no CORS headers, and a state-changing request from an unlisted origin is refused before it runs (`CORS_ORIGIN`). This sits in front of, and independent from, the CSRF check on refresh/logout.
- **W-27 Rate limits.** 600 requests/min/IP globally (health checks exempt), plus the tighter per-route limits (login, register, 2FA, refresh, import, scrape, export, deletion). Limiters are in-memory per process; with several replicas put a gateway limiter in front.
- **W-28 Audit, export, deletion.** `GET /api/audit` (admin/owner, keyset-paginated, tenant-scoped). `GET /api/export/{leads,clients,invoices}.csv` (admin/owner, 10/hour, audited) with formula neutralisation. `DELETE /api/me` (password required; the last owner is refused; their leads become unowned). `DELETE /api/tenant` (owner only; password plus typing the workspace name; revokes every session). Deletion is a SOFT delete: access ends immediately because the auth middleware re-reads user and tenant on every request. **Retention/purge of soft-deleted rows is an operational step that is not automated yet**; hard deletion of audit rows is deliberately impossible for the app role (append-only trigger).
- **W-29 Dependencies.** `npm audit --omit=dev` (what ships): 0 findings. Fixed nodemailer (high) and vitest/tinypool (critical, dev). Remaining 10 advisories are all inside `workbox-build` (a build-time dependency of vite-plugin-pwa that generates the service worker from our own config); `deepmerge` there has no patched release upstream. None of it is in the server or browser bundle.
